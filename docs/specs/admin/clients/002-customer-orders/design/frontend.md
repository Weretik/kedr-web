# Frontend design

**Verified state on 2026-10-21:** `/customers/:counterpartyId` in `clients/feature` shows three information Cards and, below them, a `CustomerOrdersPanel` from the orders domain supplied through a callback. The [Admin standard](../../../../../standards/admin/list-detail-pages.md) defines the visual composition; the current customer screen is described by [SDD 001](../../001-read-only-customers/README.md).

The section below the cards reuses the orders domain tables. Since feature-to-feature imports are prohibited by the [dependency rules](../../../../../architecture/admin/structure/dependencies.md), EN-001 was implemented: an app-level route factory passes a narrow render callback for the order panel into the clients feature, along with `counterpartyId` and URL context. The callback is implemented in `apps/admin` and uses the public orders export. The public signature is `createClientsRoutes({ renderOrdersPanel })`; `AppRouter` supplies `CustomerOrdersPanel` without a clients-to-orders import. The public clients feature dependency does not include the orders feature. Each tab query uses a server filter, and its cache key includes the customer ID and criteria; queries are refreshed after a draft mutation. Link-back context is encoded in the URL rather than stored only in memory.

Targeted automated tests cover customer isolation, independent states for both tabs, return navigation, confirmation, and empty/error states. Browser or manual review requires separate explicit permission.

**Architecture baseline:** as of 2026-10-21, `clients/feature/project.json` has the tags `scope:admin,domain:clients,type:feature`, an explicit lint target, and a public `src/index.ts`; orders Nx projects were added for this implementation. The public clients feature dependency remains free of orders imports; the app router composes both features. Targeted TypeScript checks for the clients lib/spec, five customer page tests, and Nx module boundary checks passed.
