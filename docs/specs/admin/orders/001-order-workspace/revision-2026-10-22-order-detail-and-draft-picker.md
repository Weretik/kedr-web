# Change 2026-10-22 — draft from order, product selection, and clearer details

**Status:** specification for implementation. Supplements [001](README.md) and the [previous change](revision-2026-10-22.md); completed tasks and evidence are not rewritten. New rules R-019–R-025 replace conflicting parts of R-003, R-004, R-006, and R-016 only in the scenarios described below.

## Goal and scope

The manager can create a separate draft from an already placed order, add products to an editable draft on a simple separate page, and return without losing current edits. Orders and drafts pages get clear headings, dates, and semantic statuses inspired by Devias Kit Pro Orders/Products in the visual reference library. This SDD, the current Admin UI standard, and project code remain the sources of behavior, not the reference.

This change covers React Admin, orders, and drafts only. Existing contracts for reading orders, creating/editing drafts, and product search are sufficient for the planned behavior; no new backend operation, migration, server-side 1C state change, or redesign of other modules is planned. Do not bring over payment, address, timeline, or invented fields from the reference.

## Product rules

- **R-019 — Draft from a placed order.** Order details have a «Зробити чернетку» action. It opens the same draft-save dialog used in checkout: required name, optional note (comment), and save/cancel actions. The new draft takes `counterpartyId` and all `productId/quantity` values from the open order; the name and note are entered in the dialog, without automatically copying the order comment. The source order, its 1C status, and the current local checkout set do not change. On success, open the new draft details; on failure, keep the dialog and data available for retry without creating a duplicate record.
- **R-020 — Validation timing.** In the draft dialog, an empty name is marked required, but opening the dialog shows no red state or error text. The «Зберегти» button is available for an attempt even with an empty name if other prerequisites are met. Attempting to save an empty or whitespace-only name shows a field error and sends no request. The error disappears after correction; reopening starts without an error. This applies both to a draft from the current set and a draft from an order. Other conditions preventing saving (customer/items/calculation) show a separate clear state and do not mask the name error.
- **R-021 — Localized semantic statuses.** Raw 1C values are not shown in any affected order lists or details. `Pending` → «Очікує відправлення», `Sent` → «Відправлено до 1С», `Accepted` → «Прийнято в 1С», `BusinessError` → «Помилка обробки в 1С», `TransportError` → «Помилка зв'язку з 1С», `RetryScheduled` → «Заплановано повтор», `DeadLetter` → «Потрібна перевірка». A positive state uses `success`, waiting/sending uses `info`, retry uses `warning`, and errors use `error`; color supplements the label, never replaces it. An unknown value safely displays «Невідомий стан» in a neutral color without the raw code. Visible draft quote states also need consistent text and color.
- **R-022 — Compact visual update.** On order and draft details pages, the heading, document number/name, date, and status have a clear hierarchy. The date is separated from secondary text by an MUI component/thematic styling, labeled («Створено»/«Оновлено» according to the actual field), and shown in Ukrainian in `Europe/Kyiv`. In lists, dates and statuses are easy to scan, but dates are not presented as statuses. The reference is the compact status chips and grouped facts in Devias Kit Pro Orders; preserve existing Cards, back links, information order, responsiveness, and light/dark theme. Do not introduce a separate hard-coded color palette.
- **R-023 — Separate product selection for a draft.** Remove the `ProductPicker` with its «Знайти й додати товар» field from draft editing. The «Додати товар» button navigates to a separate product-selection page in the context of this draft. It shows search, name, current catalog price, stock/availability, and an add action; it does not show photos, category controls, or the full catalog page. Search and pages use the existing server-side products list, so a product beyond the first 20 can be found. An already added item is marked and cannot be duplicated. Adding changes only the editable draft form; the server PUT occurs after «Зберегти зміни» on the edit page. Missing price/zero stock are shown clearly; the server quote after adding determines whether saving is possible.
- **R-024 — Preserve edits while navigating.** Navigating from draft editing to the products page and back preserves the unsaved name, note, customer, items, and quantities within that open editing flow. Returning does not send a PUT or replace edits with a repeated GET. Directly opening the product-selection URL loads the source draft; 404, product-list error, and `409` on final save have separate states. Changes to another draft are not mixed into the current one.
- **R-025 — Customer after navigating to the catalog.** On `/orders/new`, the selected `counterpartyId` is preserved with the current local set scenario after navigating to the catalog and closing the tab in the same browser profile. On return or reopening, it is restored without requiring another selection. An explicit `customerId` in the URL (for example, from a draft) takes precedence; manually changing the customer updates the stored ID. After successful checkout or saving the current set as a draft, the stored selection is cleared along with the set; copying an individual order to a draft does not clear it. Do not store the name, contact details, prices, or tokens in browser storage. Unavailable/corrupted storage does not block checkout and shows a clear warning. An ID for a customer missing after 1C synchronization cannot be silently used for a new request.

## Verified baseline, decisions, and code boundaries

- Current routes: `orders/:orderId`, `orders/new`, `orders/drafts/:draftId/edit`. `OrderDetailPage` currently only reads details. `DraftEditPage` keeps fields locally and renders the app-owned `ProductPicker`, which searches only the first 20 products through MUI Autocomplete. `OrderDocumentView` shows the raw status and a date in the browser's time zone. `OrderListGrid` also shows the raw 1C state. `SaveDraftDialog` shows an empty-name error immediately on opening. `current-order-set.ts` stores only items; `NewOrderPage` keeps the customer only in React state.
- Use existing `getAdminWorkspaceOrderById`, `createAdminOrderDraft`, `getAdminOrderDraftById`, `updateAdminOrderDraft`, `getAdminProducts`, `getAdminCustomers`, and quote operations. The current machine snapshot comes from backend commit `c03118d63f7cafe1f44b755bd0ee84d7cb1cf62f` (`docs/contracts/openapi/SOURCE.md`); this increment needs no new operation. `createAdminOrderDraft` accepts `title,note?,counterpartyId,lines` and UUID `Idempotency-Key`. Do not copy price/total from the source order into the POST; the server validates and calculates the draft from current data. Transport DTOs remain in `orders/data-access`, and components consume mapped models. `getAdminProducts` already returns pages, name, nullable `price`, `stock`, and `inStock` through products data-access.
- The current API sends machine 1C codes; localization is only a UI presentation mapping. Do not change the backend enum or HTTP response. One `code → label + MUI color` map belongs in orders UI/model and is used by both list and details; `unknown` has a safe fallback. Prefer MUI `Chip`, `Card`, `Typography`, `Button`, `Alert`, `DataGrid`, and theme palette over custom widgets. For order creation date and draft creation/update dates, use the actual fields; do not substitute one for another.
- For product selection, add a nested route `orders/drafts/:draftId/edit/products` under a shared edit-state owner. It preserves fields when navigating between edit and product selection; on direct entry it loads the draft. Clicking «Додати» does not automatically save name and quantity to the server. Remove the existing `ProductPicker` only from draft editing; do not duplicate product API code in orders. Store search/page parameters in the selection page URL, with debounce and server `rowCount`.
- For the checkout customer, extend the versioned storage for the current set or add a neighboring versioned record under the same state owner. Before implementation, specify migration of the old `version:1` payload without losing items, explicit URL precedence, and `storage` event behavior across tabs. Store only the ID; validate it against the existing customer API after restoration. A restored ID does not prove that the customer still exists. Order → draft copying bypasses clearing the local set in `useSaveDraft`.
