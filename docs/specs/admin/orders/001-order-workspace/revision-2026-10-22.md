# Change 2026-10-22 — Admin cart, lists, and checkout

**Status:** implementation of TS-007 and the frontend part of TS-008 has been checked against the code; the backend date contract and provider snapshot were synchronized after the initial evidence was recorded (`c03118d`). This increment supplements the [initial specification](README.md); historical R-001–R-010, SC-001–SC-008, and implementation evidence remain a record of the previous state. The requirements below replace conflicting parts of R-001, R-002, R-005, and R-007 only for this new increment.

## Goal and scope

The manager sees the number of items in the current set in the header, can quickly proceed to checkout, works with lists using search and dates, and sees clear names and an estimated total before confirmation. Draft saving and checkout open separate dialogs. Changes concern Admin React; Mobile and Storefront are out of scope. The header count is the number of **distinct items**, not the sum of product units.

## Product rules

- **R-011.** The Admin header shows an MUI cart icon with a badge for the number of items in the current local set. Clicking it navigates to `/orders/new`; the number updates after adding, changing, or removing an item and after successful checkout/save.
- **R-012.** Neither tab on the main orders page shows a customer picker. Search remains server-side: orders — number/customer; drafts — name/customer. The field uses the same MUI X composition with a search icon as the products list; helper text disappears after input and does not become a floating label.
- **R-013.** Both tabs on the main page have independent date ranges in the URL. Orders are filtered by creation date, drafts by creation date. Start and end are inclusive for calendar dates in the `Europe/Kyiv` time zone; an empty bound does not restrict the result set. An invalid or reversed range is not sent. Changing the range resets the page to the first one; the server calculates `totalRecords` after filtering and before pagination.
- **R-014.** The customer picker displays only the name, without an ID; selection is identified by the immutable `counterpartyId`. Users can find and select any customer, not just the first 20. The list loads page by page, fetching more on scroll; the already selected customer remains visible even when outside the current page.
- **R-015.** Each item in the set shows its name, quantity with «+»/«−» buttons, unit price, line total, and grand total. After customer selection and receipt of server prices, changing quantity immediately updates the visible estimated total from loaded prices; a new server quote is requested in parallel. If a price is not yet loaded, unavailable, or pricing depends on the changed quantity, the UI must not present an estimate as confirmed. The product name must be available even before the first quote through existing catalog data or a targeted read; an ID is not a substitute for the name.
- **R-016.** Three MUI buttons remain below the product list: «Додати з каталогу» opens the catalog; «Зберегти як чернетку» opens a dialog with a required name, optional note, and «Зберегти»/«Скасувати» actions; «Оформити замовлення» opens a dialog with an optional comment, the currently confirmed total, and «Відправити»/«Скасувати» actions. Permanently visible forms below the list are removed. A failed operation does not clear the set.
- **R-017.** Browser prices and totals are estimates; the server remains authoritative for final calculation through `quoteAdminWorkspaceOrder` and `createAdminWorkspaceOrder`. Submission is unavailable until a current quote exists for the current customer and set; `409 quote_changed` shows the new total and requires reconfirmation in the same flow.
- **R-018.** All affected screens use MUI/MUI X components, the theme, Ukrainian labels, and accessible icon names. Do not create custom equivalents of existing MUI Badge, IconButton, Dialog, TextField, Autocomplete, DataGrid, and DatePicker components.

## Verified baseline and design

- `AdminTopBar` currently does not show the set. `current-order-set.ts` stores only `productId/quantity` in browser storage; do not store prices or customer data there. The app router already has `/orders/new` and a callback for adding from Products.
- `OrderTables` is shared by the main page and customer details. New date parameters must be separate per tab and must not mix with the fixed `counterpartyId` of the customer panel. Customer-panel differences are defined in [its SDD](../../clients/002-customer-orders/README.md).
- `CustomerPicker` currently reads only page 1/size 20 and displays the ID in the name. Use the existing `getAdminCustomers` with server search/pagination and `getAdminCustomerById` for the current selection; no separate full-list endpoint is planned.
- `OrderLineEditor` already shows the server quote, but replaces names with `ID` when no quote exists and changes quantity only through a numeric field. Catalog data can provide the name; customer-specific prices come from the quote. Local estimated recalculation does not change API DTOs or store prices in browser storage.
- Search is implemented with MUI X `QuickFilter`/`QuickFilterControl` following the products table pattern, without importing the products feature into orders. Date ranges use MUI X `DatePicker`, `LocalizationProvider`, and `AdapterDayjs`; the lockfile pins `@mui/x-date-pickers` 9.10.1 and `dayjs` 1.11.13.
- Architecture boundaries: `apps/admin` owns shell/customer adapter composition; `orders/feature` owns URL, dialogs, and state; `orders/ui` owns MUI presentation; `orders/data-access` owns generated transport/runtime mapping. Do not move HTTP into UI.

## API and dependencies

| Order | Operation                                                                        | Decision                                                                                                                               |
| ----- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 1     | `getAdminWorkspaceOrders`                                                        | backend adds `createdFrom`/`createdTo` range to server pagination; frontend synchronizes snapshot after the versioned backend contract |
| 1     | `getAdminOrderDrafts`                                                            | backend adds `createdFrom`/`createdTo` based on `CreatedAtUtc`                                                                         |
| 2     | `getAdminCustomers`, `getAdminCustomerById`                                      | existing contract is sufficient for all customer pages and restoring selection                                                         |
| 2     | `quoteAdminWorkspaceOrder`, `createAdminWorkspaceOrder`, `createAdminOrderDraft` | forms and estimated calculations do not change DTOs; final price remains server-owned                                                  |

**Date contract limitation:** the UI passes `createdFrom` and `createdTo` through `orders.api.ts`, but the current provider snapshot `docs/contracts/openapi/sales/admin-order-workspace.openapi.yaml` does not declare these query parameters for `getAdminWorkspaceOrders` and `getAdminOrderDrafts`; generated types also do not confirm them. Therefore frontend date controls, URL state, and request construction are implemented, but backend compatibility and inclusive `Europe/Kyiv` boundaries are not confirmed by this snapshot. After the provider OpenAPI changes, synchronize the snapshot and generated types using the [workflow](../../../../contracts/README.md); do not edit generated artifacts manually.
