### SEO-001 — High: путь из каталога к товару заканчивается 404

**Подтверждено HTTP и исходниками.** Категория `/uk/catalog/zavisy` содержит ссылку `/uk/product/class-cap-d14-46-ab`; оба языковых варианта товарного адреса отвечают 404. `/uk/catalog/product/class-cap-d14-46-ab` отвечает 308, а конечный новый адрес — 404. ItemList содержит те же назначения.

Источники: [product-card.tsx:19](E:/RiderProjects/kedr-web/libs/site/catalog/ui/src/lib/product/product-card.tsx:19), [catalog-json-ld.ts:42](E:/RiderProjects/kedr-web/libs/site/catalog/seo/src/lib/json-ld/catalog-json-ld.ts:42), [next.config.ts:50](E:/RiderProjects/kedr-web/apps/site/next.config.ts:50). Product route отсутствует в проверенном inventory и остаётся шагом 4 [плана миграции](E:/RiderProjects/kedr-web/docs/specs/site/migration/README.md).

Это запланированная часть миграции, но для переключения магазина она является блокером: посетитель и робот не могут перейти от ассортимента к товару. Рекомендация — завершить product route, серверные данные и canonical/языковые пары, затем Product/Offer из реальных цены, валюты и наличия. Проверить доступность новых URL и конечные назначения всех old product redirects. Не добавлять Product schema на список в попытке заменить отсутствующую карточку. Такой путь category → product соответствует [рекомендациям Google по структуре магазина](https://developers.google.com/search/docs/specialty/ecommerce/help-google-understand-your-ecommerce-site-structure); требования к разметке описаны отдельно в [merchant listings](https://developers.google.com/search/docs/appearance/structured-data/merchant-listing).

**Владелец:** frontend/product + backend для недостающих полей. **Срок:** до cutover. **Приёмка:** реальный товар 200 в обоих языках, старый URL приводит к нему, видимые данные и JSON-LD совпадают, товар находится через навигацию и согласованный sitemap.

**Владелец:** frontend/content + владелец продукта для региональной модели. **Срок:** до cutover. **Приёмка:** каждая публикуемая ссылка приводит к предусмотренному доступному назначению; private routes сохраняют отдельную политику noindex.

### SEO-003 — Medium: пустые фильтры и отсутствующая пагинация отвечают 200

**Подтверждено HTTP и исходниками.** `/uk/catalog/zavisy?page=9999` и `/uk/catalog/zavisy?priceFrom=9999999` отвечают 200 с canonical `/uk/catalog/zavisy`. В обоих случаях нет ItemList с товарами. Локальный robots — noindex, nofollow; по production-builder политика этих вариантов — noindex, follow.

Это сознательное текущее решение SDD/SEO architecture, а не случайная ошибка переноса. Однако [seo-rules.md:19](E:/RiderProjects/kedr-web/docs/standards/site/seo-rules.md:19) запрещает 200 для empty filters, а [Google faceted navigation guidance](https://developers.google.com/crawling/docs/faceted-navigation) рекомендует 404 для нулевых комбинаций и несуществующих страниц пагинации.

Рекомендация — принять единое решение и согласовать SDD, стабильное правило, реализацию и тесты. Предпочтительный SEO-вариант: существующие категории с ассортиментом — 200, действительно несуществующие комбинации/страницы — 404 под запрошенным URL с понятной кнопкой сброса, без redirect на общую ошибку. Нулевой результат поиска — отдельный служебный сценарий; не распространять правило механически на любую форму поиска. Noindex помогает исключить варианты из поиска, но сам по себе не делает HTTP 200 ответом «не найдено» и не прекращает расход обхода.

**Владелец:** frontend/catalog + SEO/владелец политики. **Срок:** до SEO-финиша миграции. **Приёмка:** таблица indexability/status/canonical одна для кода и документов; подтверждены непустая page 2, page past-end, пустой фильтр и неизвестная категория.

### SEO-004 — Medium: проверка переноса query при переименовании категории

**Подтверждено HTTP в обоих языках.** `/uk/catalog/zavisi-900001?page=2` отвечает 308 на `/uk/catalog/zavisy` без `?page=2`, затем 200 с canonical первой страницы. RU-версия теряет параметр аналогично. При прямом обращении к новому `/uk/catalog/zavisy?page=2` вторая страница существует и имеет собственный canonical. Это потеря выбранной страницы, а не отсутствие page 2.

Дублирующихся title среди этих 120 canonical страниц нет. Description каталога стоит описать как выбор разделов и переход к ассортименту; description главной — как представление компании и общего предложения. **Владелец:** content/design/frontend. **Срок:** SEO-финиш или следующая итерация. **Приёмка:** понятные summaries, корректные язык/URL, доступные реальные изображения; без механического повторения ключей.

## Что уже сделано правильно

1. **Индексация защищена окружением.** Локальные публичные страницы дают `noindex, nofollow`, `/robots.txt` — `User-Agent: * / Disallow: /`. Это ожидаемое состояние до переключения, а не SEO-дефект. Для production нужны одновременно `SITE_ENV=production` и `SITE_INDEXING=true` ([site-config.ts](E:/RiderProjects/kedr-web/libs/site/core/config/src/lib/site-config.ts), [robots-policy.ts](E:/RiderProjects/kedr-web/libs/site/core/seo/src/lib/metadata/robots-policy.ts)).
2. **Canonical и языковые версии централизованы.** UA и RU ссылаются на себя, нет canonical RU→UA. В контрольных парах есть `uk-UA`, `ru-UA` и HTML `x-default` на UA; язык документа соответствует маршруту. Это согласуется с [Google localized versions](https://developers.google.com/search/docs/specialty/international/localized-versions).
3. **Контент приходит с сервера.** H1, договор, статьи и товарные href находятся в HTTP-ответе. Browser DOM подтверждает раскрытие потокового содержимого. Поисковую информацию не надо получать только клиентским fetch после открытия страницы.
4. **Пагинация имеет свой canonical.** Существующая вторая страница сохраняет `?page=2`; navigation — обычные href. Не требуются `rel=next/prev` ради Google.
5. **Canonical-множество и sitemap.** По двум состояниям сайта сопоставлены 120 URL на production origin с UK/RU alternates. Все 120 canonical назначений из объединения снимков проверены локально: конечный HTTP 200. Однако последний XML содержит 34 URL; в нём отсутствуют 86 адресов категорий. До добавления галереи был полный XML с 118 адресами. Это наблюдаемая деградация sitemap, SEO-005; доступность страниц и полнота XML оцениваются отдельно. Совпадение canonical и языковых пар проверено автоматически. Search, filters, private routes и запланированные product pages в XML не перечислены как готовые страницы. Отсутствие `x-default` именно в sitemap не является отдельной проблемой при корректных HTML alternates. Без достоверного updatedAt lastModified не выдумывается.
6. **Разметка соответствует назначению.** Organization — общая сущность, WebSite — главная, BreadcrumbList — соответствующие страницы, ItemList — реальные листинги, Article — статьи. В проверенных JSON-LD нет синтаксических ошибок; это не равно гарантии eligibility Google Rich Results. Отсутствие необязательного author само по себе не является ошибкой Article; [Google Article guidance](https://developers.google.com/search/docs/appearance/structured-data/article).
7. **Коммерческие факты не подменяются.** Телефон/почта/город приходят из общего COMPANY. Нет придуманных отзывов, адресов филиалов, дат обновления, рейтингa или фиктивных Product/Offer. Наличие только Organization, без LocalBusiness, допустимо, пока публичные бизнес-данные не позволяют достоверно расширить тип.
8. **Проверенные old URLs в основном работают.** `/` и trailing slash нормализуются 308; старые категории/list/search ведут к новым страницам, article ID — 301 к slug. 308 является постоянным редиректом и [Google обрабатывает его как 301](https://developers.google.com/crawling/docs/troubleshooting/http-status-codes). Неработающее назначение товара разобрано отдельно.

Для расширения в Google Shopping/Merchant Center сначала нужны готовые карточки и достоверные торговые данные, после чего можно оценивать feed и правила программы.

После cutover целесообразны ежедневный контроль ошибок/редиректов в первую неделю, повторный технический проход спустя неделю и оценка GSC по сопоставимым периодам через 2–4 недели. Переобход и изменения в поиске не происходят мгновенно; падение/рост нельзя приписывать одному изменению без сопоставления данных. [Google: site moves](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes).
